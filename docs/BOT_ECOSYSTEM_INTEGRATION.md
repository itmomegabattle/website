# Экосистема сайта, Telegram-ботов и Mini App

Дата актуализации: 6 июля 2026  
Статус: архитектурная фиксация по ответам и текущему видению. Сейчас фокус разработки — сайт. Боты делаются параллельно, но сайт должен быть готов к будущей связке.

## 1. Короткий вывод

В экосистеме будет ровно 2 Telegram-бота:

1. Бот для участников.
2. Бот для мегаорганизаторов.

Это два отдельных бота, не один бот с разными режимами.

Авторизация в будущем:

- основной вариант — ITMO.ID;
- запасной/дополнительный вариант — Telegram;
- если ITMO.ID не дадут вовремя, временно живём через Telegram-связку.

Источник истины по ключевым данным должен быть не “бот” и не “фронт”, а общая база/backend. Сайт, Mini App и оба бота должны читать и менять данные через один общий слой.

Рекомендуемая схема:

```text
Сайт
Telegram Mini App
Бот участников
Бот оргов
        ↓
    Backend API
        ↓
Supabase Postgres + Storage
```

На ближайшем этапе можно продолжать концентрироваться на сайте, но проектировать сайт уже так, будто backend/API будет единым центром.

## 2. Что значит “источник истины”

“Источник истины” — это место, где лежит главная версия данных, которой все остальные части системы доверяют.

Пример:

- если участник изменил факультет на сайте;
- бот участников показывает профиль;
- бот оргов считает статистику;
- граф знакомств строится на сайте;
- рейтинг считает баллы;

то все эти части должны смотреть в одну и ту же запись профиля, а не хранить разные версии.

Плохо:

```text
Сайт хранит профиль у себя
Бот участников хранит профиль у себя
Бот оргов хранит профиль у себя
Рейтинги считают по своему JSON
```

Так появятся расхождения: на сайте КТУ, в боте ТИНТ, в рейтинге старый ник, в графе другой id.

Хорошо:

```text
profiles в БД — главная версия профиля
friendships в БД — главная версия знакомств
score_events в БД — главная история баллов
nfc_tags в БД — главная версия меток
event_registrations в БД — главная версия регистраций
```

Сайт и боты могут иметь кеш или локальное представление, но не должны быть главным владельцем критичных данных.

## 3. Уже зафиксированные решения

### 3.1. Количество ботов

Ровно 2:

- бот для участников;
- бот для мегаорганизаторов.

### 3.2. Формат

Это 2 отдельных Telegram-бота.

### 3.3. Mini App

Mini App нужен в обоих ботах.

Также уже есть первоначальная версия Mini App для бота оргов, её нужно будет доработать и связать с сайтом/backend.

### 3.4. Авторизация

Основной вариант:

- ITMO.ID.

Дополнительный/резервный:

- Telegram.

Логика:

- если ITMO.ID дадут — делаем ITMO.ID обязательным;
- если ITMO.ID не дадут вовремя — временно идём через Telegram;
- Telegram всё равно нужен для связки с ботами.

### 3.5. Роли

На сайте:

- админ сайта;
- орг;
- участник.

При этом сейчас “орг” по смыслу равен “админ” для операционных действий.

В боте оргов:

- глав орг;
- орги;
- отвы.

В боте участников:

- участники;
- админы, то есть орги.

Роли выдаются вручную.

Сложная ролевая система пока не нужна, но архитектурно нужно оставить место для расширения.

### 3.6. Управление ролями

Нужно:

- на сайте иметь админское управление ролями;
- в боте оргов/Mini App иметь управление или хотя бы отображение ролей;
- роли должны храниться в общей базе;
- не должно быть так, что сайт считает человека админом, а бот — нет.

### 3.7. Кто что может делать

По текущим ответам:

- админские функции сайта доступны оргам/админам;
- удаление/бан/модерация — орги/админы;
- назначение задач — любой орг;
- создание собраний — любой орг;
- управление дедлайнами — орги;
- задачи и дедлайны видят/используют орги + отвы в боте оргов;
- участники в основном зрители, кроме действий участника: профиль, NFC, регистрации, валюта/уровни, взаимодействия.

### 3.8. Данные из ITMO.ID

Пока нужны:

- ИСУ;
- ФИО.

Мегафак актива хранится у нас отдельно и не связан напрямую с ITMO.ID.

То есть ITMO.ID подтверждает личность, а проектная принадлежность к мегафаку/активу — наша внутренняя сущность.

### 3.9. Уровни

Уровней планируется от 3 до 7.

Уровень растёт по баллам, логика похожа на XP.

Нужны разные уровни/пороги.

Баллы могут выдаваться:

- автоматически;
- админом/оргом.

Нужна история начислений, чтобы потом не было хаоса и накруток.

## 4. Бот для участников

### 4.1. Назначение

Бот для участников — это персональный помощник участника Megabattle.

Основные функции из схемы:

- уровни;
- внутренняя валюта;
- новости;
- регистрация на мероприятия;
- информационная справка для перваков;
- сбор статистики;
- связь регистрации с сайтом;
- отдел вайба.

### 4.2. Уровни

Идея:

- участник получает баллы/XP;
- за повышение уровня может выдаваться подарок, валюта, мерч или другой бонус;
- первый уровень — первое мероприятие IMB;
- последний уровень — условно “всё мерч за семестр/год”.

Возможные источники XP:

- знакомства;
- бинго;
- количество часов в ИТМО или проектной активности;
- рефералки;
- прохождение всех станций на квизе;
- особые ачивки.

Особые ачивки из схемы:

- преза про Megabattle на софтах;
- снять TikTok/Reels/Shorts для аккаунта IMB.

### 4.3. Внутренняя валюта

Идея:

- система переводов через бота;
- перевод может быть между участниками;
- одноразовые коды или NFC-метки могут давать валюту;
- валюта нужна для экономики проекта и “отдела вайба”.

Нужно решить позже:

- название валюты;
- можно ли переводить всем всем;
- есть ли комиссии/лимиты;
- можно ли уходить в минус;
- какие товары/бонусы покупаются;
- кто может начислять вручную;
- нужна ли история транзакций публично или только админу.

### 4.4. Новости

Бот должен отправлять:

- важные новости по текущему сезону;
- апдейты;
- анонсы мероприятий;
- напоминания.

Нужно:

- единый источник новостей;
- расписание отправки;
- возможность отправить по всем;
- возможность отправить по мегафаку;
- возможность отправить только зарегистрированным на мероприятие.

### 4.5. Регистрация на мероприятия

Идея:

- бот может подтянуть регистрацию с сайта/ITMO Events;
- регистрация на квиз и другие события может идти через бота;
- сайт и бот должны видеть одну регистрацию.

Источник истины:

- `event_registrations` в базе/backend.

Не должно быть двух разных регистраций: “на сайте зарегистрирован, в боте нет”.

### 4.6. Информационная справка для перваков

Бот должен отвечать:

- про их мегафак;
- контакты ответственных;
- справка по мероприятиям;
- что такое мероприятие и для кого;
- правила Megabattle;
- что такое мегабаллы;
- как попасть на отборы на концерт;
- что делать новичку.

Эти тексты лучше хранить не в коде бота, а в базе/админке как FAQ/knowledge base.

Минимальная сущность:

```text
bot_faq_items:
  id
  audience
  category
  question
  answer
  status
  sort_order
```

### 4.7. Сбор статистики

Нужна статистика:

- посещений мероприятий, которые проходят не через ITMO Events;
- общего количества валюты на мегафак;
- активности участников;
- возможно посещений/регистраций/сканов.

Источник:

- события в базе;
- check-ins;
- score events;
- bot events.

### 4.8. Связь регистрации с сайтом

Публичная визитка через NFC уже есть на сайте. Бот должен уметь:

- открыть сайтовую визитку;
- связать Telegram аккаунт с профилем;
- подтягивать профиль;
- возможно показывать quick actions.

### 4.9. Отдел вайба

Идеи:

- отслеживать общий баланс факультета для балансировки экономики;
- валентинки;
- смешные фото;
- короткие временные фото;
- социальные механики;
- локет-подобный режим.

Важно:

- всё, что связано с временными фото, должно иметь автоудаление;
- хранение максимум час;
- нужна политика приватности;
- нужен контроль размера файлов;
- нужен репорт/модерация, если фото могут быть неприятными.

## 5. Бот для мегаорганизаторов

### 5.1. Назначение

Бот для оргов — рабочий инструмент штаба/организаторов.

Основные функции из схемы:

- др/напоминания;
- задачи и дедлайны;
- отметки по занятости оргов на неделю;
- назначение собраний;
- вайбик;
- дополнительные сценарии в боте для ответственных.

### 5.2. ДР и напоминания

Идеи:

- уведомлять за 2 дня всех, кроме именинника;
- начинать автоматом сбор денег на подарок с подписью “на ДР”;
- не забыть про общую карту оргов для сбора денег;
- сим-карта/общая карта, если понадобится.

Нужно решить позже:

- где хранить даты рождения;
- кто видит дни рождения;
- как не нарушить приватность;
- можно ли отключить поздравления;
- кто создаёт сбор;
- как фиксируются переводы.

### 5.3. Задачи и дедлайны

Идея:

- один человек может назначить задачу и дедлайн;
- задача имеет блоки/подзадачи;
- прогресс может проставлять человек, которому принадлежит задача;
- нужна визуализация дедлайнов;
- нужно видеть загруженность конкретного орга;
- бот напоминает и пингует по задаче;
- бот снимает функцию “человека, который долбит за задачу”.

Минимальные сущности:

```text
tasks:
  id
  title
  description
  status
  created_by_profile_id
  assignee_profile_id
  responsible_profile_id
  due_at
  priority
  created_at
  updated_at

task_items:
  id
  task_id
  title
  status
  sort_order

task_updates:
  id
  task_id
  author_profile_id
  progress_percent
  comment
  created_at
```

### 5.4. Занятость оргов

Уже есть первоначальная версия Mini App, где проставляется занятость на неделю.

Нужно:

- доработать Mini App;
- хранить занятость в общей базе;
- автоматически выбирать самые свободные дни;
- использовать это при назначении собраний;
- показывать, когда можно/нельзя ставить встречу.

Минимальная сущность:

```text
organizer_availability:
  id
  profile_id
  week_start_date
  day_of_week
  time_slot
  status
  comment
```

### 5.5. Назначение собраний

Идея:

- организатор назначает собрание;
- бот предлагает наиболее выгодную дату по занятости;
- можно назначить свою дату;
- задаётся тема;
- бот заранее пингует;
- указывается время начала и конца.

Минимальные сущности:

```text
meetings:
  id
  title
  description
  organizer_profile_id
  starts_at
  ends_at
  location
  status
  created_at

meeting_participants:
  meeting_id
  profile_id
  status
```

### 5.6. Вайбик

Идеи:

- добавить в бота участников и оргов минимальный вайбик;
- добавить слух/заметку, которая записывается в общий “гудок”;
- в случайный момент отправить смешную фотку;
- фотки сохраняются в общий архив/выводятся в виджет;
- отправка валентинок другим пользователям.

Нужно осторожно:

- если фото/слухи пользовательские — нужна модерация;
- если есть публичный вывод — нужен репорт;
- временные фото должны удаляться;
- нельзя превращать в токсичную штуку.

### 5.7. Дополнительные сценарии для ответственных

Идеи:

- пинговать ответственных по дедлайнам для мегаоргов;
- отправка музыки на визитку;
- отправка технического сценария;
- другие сценарии под концерты/мероприятия.

Доступ:

- орги + ответственные в боте оргов.

## 6. Роли и права

### 6.1. Простая модель на ближайший этап

Пока сложная ролевая система не нужна.

Минимум:

```text
site_role:
  participant
  organizer
  admin

org_bot_role:
  head_organizer
  organizer
  responsible

participant_bot_role:
  participant
  admin
```

Но лучше не хранить это тремя разрозненными строками в разных местах, а сделать нормальную таблицу:

```text
profile_roles:
  id
  profile_id
  scope
  role
  granted_by_profile_id
  created_at
```

Где:

- `scope = site`
- `scope = org_bot`
- `scope = participant_bot`

Так можно вручную выдавать роли и не ломать систему, если потом появятся новые.

### 6.2. Кто выдаёт роли

По текущему решению:

- роли выдаются вручную;
- выдавать должен админ/орг с правами;
- на сайте нужен UI для ролей;
- в боте оргов/Mini App тоже нужен UI или связка.

### 6.3. Что делать сейчас на сайте

Сейчас достаточно:

- оставить `is_admin`;
- добавить понимание `org/participant` на уровне профиля;
- в будущем мигрировать на `profile_roles`;
- не зашивать права только в frontend.

## 7. Авторизация и привязка аккаунтов

### 7.1. ITMO.ID

ITMO.ID — основной способ идентификации, если доступ дадут.

Нужные данные:

- ИСУ;
- ФИО;
- уникальный subject/id пользователя.

Сайт должен:

- уметь связать ITMO.ID с текущим профилем;
- не потерять NFC;
- не потерять соцсети;
- не потерять баллы;
- не потерять дружбы;
- не потерять истории/регистрации.

### 7.2. Telegram

Telegram нужен:

- для обоих ботов;
- для Mini App;
- для уведомлений;
- как fallback auth, если ITMO.ID задержится.

Нужна таблица:

```text
telegram_accounts:
  id
  profile_id
  telegram_user_id
  username
  first_name
  last_name
  language_code
  linked_at
  last_seen_at
```

### 7.3. Связка ITMO.ID + Telegram

Главная задача:

- понять, что человек с ITMO.ID и человек в Telegram — один и тот же профиль.

Варианты:

1. Пользователь входит на сайте через ITMO.ID, потом нажимает “привязать Telegram”.
2. Пользователь открывает Mini App, проходит Telegram verify, потом сайт предлагает связать ITMO.ID.
3. Если ITMO.ID нет, Telegram временно создаёт профиль, который потом можно связать с ITMO.ID.

## 8. Что сайт должен подготовить уже сейчас

Так как сейчас фокус на сайте, нужно не писать весь bot backend прямо сейчас, а подготовить правильные точки стыковки.

### 8.1. Профиль

Добавить/предусмотреть:

- стабильный `profile.id`;
- ИСУ;
- ФИО;
- мегафак/факультет как наша внутренняя сущность;
- Telegram username;
- Telegram account binding позже;
- роли.

### 8.2. Роли

Подготовить:

- хотя бы поле/таблицу для роли участник/орг/админ;
- UI в админке;
- не завязывать всё только на `is_admin`.

### 8.3. События

Подготовить:

- registrations table;
- статус регистрации;
- связь профиля и мероприятия;
- источник регистрации: site/bot/itmo_events/import.

### 8.4. Баллы

Подготовить:

- score events;
- причина начисления;
- кто начислил;
- автомат/ручное;
- связь с событием/действием.

### 8.5. Граф

Подготовить:

- friendships как источник истины;
- endpoint/API позже;
- frontend не должен рассчитывать права добавления дружбы.

### 8.6. Уведомления

Подготовить:

- таблицу notifications;
- тип уведомления;
- кому отправить;
- канал;
- статус доставки.

### 8.7. Temporary photos

Подготовить:

- таблицу временных фото;
- срок истечения;
- storage path;
- future cleanup job.

## 9. Что пока не делаем

По текущей договорённости сейчас не надо глубоко фиксировать:

- все тексты FAQ;
- точную экономику валюты;
- точные подарки за уровни;
- точные формулы рейтинга;
- точные сценарии каждого бота;
- полный дизайн Mini App;
- все edge cases Telegram.

Сейчас цель — сайт и архитектурная готовность к связке.

## 11. API, который понадобится для связки

### 11.1. Auth

```text
GET  /auth/itmo/start
GET  /auth/itmo/callback
POST /auth/telegram/verify
POST /auth/logout
GET  /me
```

### 11.2. Profiles

```text
GET   /profiles/:id
PATCH /profiles/me
POST  /profiles/me/avatar
POST  /profiles/me/link-telegram
```

### 11.3. Roles

```text
GET  /admin/roles
POST /admin/profiles/:id/roles
DELETE /admin/profiles/:id/roles/:roleId
```

### 11.4. Events

```text
GET  /events
```

## 13. Ближайшее действие для сайта

Пока боты делаются параллельно, сайту нужно сделать 5 вещей, чтобы потом связка была без боли:

1. Начать backend-каркас.
2. Подготовить нормальную модель ролей.
3. Подготовить registrations/score_events/friendships как серверные сущности.
4. Не развивать админские опасные действия только на frontend.
5. Оптимизировать mobile hero/preloader, потому что это P0-блокер публичного запуска.

## 14. Итог

Экосистема выглядит реалистично, но только при условии, что:

- сайт не будет единственным местом бизнес-логики;
- боты не будут жить каждый со своей отдельной базой;
- Telegram и ITMO.ID будут связаны в одном профиле;
- роли будут едиными;
- баллы/валюта/регистрации/дружбы будут храниться централизованно;
- backend появится до глубокой интеграции с ботами.

Главный принцип: сайт, оба бота и Mini App — это разные интерфейсы к одной системе, а не три разных продукта.

## 15. Примерный бюджет инфраструктуры

Дата оценки: 6 июля 2026.  
Цены нужно перепроверять перед оплатой, потому что тарифы облаков и курсы валют могут меняться.

### 15.1. Главный вывод по деньгам

Для ближайшего запуска не нужно закладывать огромный бюджет.

Реалистично:

- MVP/тест: от 0 до 2 000 ₽/мес;
- нормальный аккуратный прод: примерно 3 000–8 000 ₽/мес;
- прод с запасом, мониторингом и backend: примерно 8 000–18 000 ₽/мес;
- дорогой сценарий с платными командными тарифами Vercel/Sentry/Render: 20 000+ ₽/мес.

Я бы целился в вариант:

```text
Vercel Hobby/Pro для сайта
Supabase Pro для базы/storage
Timeweb Cloud или Railway для backend
Sentry Free сначала
UptimeRobot/аналог free сначала
```

### 15.2. Домен

Домен — самая критичная покупка, потому что NFC-метки будут физически вести на него.

Оценка:

- `.ru` / `.рф`: примерно 200–1 500 ₽/год, зависит от регистратора и акций;
- `.com`: примерно 1 200–3 000 ₽/год;
- редкие/красивые домены могут стоить сильно дороже;
- лучше сразу купить на 5–10 лет и включить автопродление.

Рекомендация:

- купить основной домен минимум на 5 лет;
- включить автопродление;
- доступ держать не на одном человеке;
- для NFC использовать только постоянный домен, не vercel-preview URL.

Оценка на 5 лет:

```text
.ru/.рф: примерно 1 000–7 500 ₽
.com: примерно 6 000–15 000 ₽
```

### 15.3. Frontend hosting

Сейчас сайт на Vercel.

Варианты:

1. Vercel Hobby:
   - $0/мес;
   - может хватить для старта;
   - нужно следить за лимитами и коммерческими условиями.

2. Vercel Pro:
   - $20/мес за developer seat;
   - больше лимитов;
   - лучше для стабильного продакшена.

Оценка:

```text
Hobby: $0/мес
Pro: $20/мес ≈ 1 800–2 200 ₽/мес при грубом курсе 90–110 ₽/$
```

Для ближайшего запуска можно оставить Hobby, если лимиты и правила использования подходят. Если запускаемся публично и хотим спокойнее — Pro.

### 15.4. Supabase

Supabase нужен как:

- Postgres;
- Storage;
- Auth на переходный период;
- RLS;
- управление данными.

Варианты:

1. Free:
   - $0/мес;
   - годится для разработки и раннего теста;
   - ограниченные ресурсы.

2. Pro:
   - примерно от $25/мес + usage;
   - нормальный вариант для продакшена.

Оценка:

```text
Free: $0/мес
Pro: $25/мес ≈ 2 250–2 750 ₽/мес
С запасом по storage/egress: $25–50/мес ≈ 2 250–5 500 ₽/мес
```

Для 500 средних пользователей и пиков до 3000 Supabase Pro должен быть нормальной отправной точкой, если видео не хранить и не раздавать через Supabase бездумно.

Важно:

- hero-видео и крупные публичные ассеты лучше держать на Vercel/CDN/static, не в Supabase Storage;
- пользовательские фото, аватары, истории, временные фото — Supabase Storage;
- временные фото обязательно чистить cron-задачей.

## 16. Ценовой вывод

Финансово проект не выглядит дорогим на старте. Самые опасные статьи расходов не backend и не боты, а:

- тяжёлые видео;
- бесконтрольный storage временных фото;
- egress/CDN;
- платные командные тарифы;
- ошибки в архитектуре, из-за которых потом придётся всё переписывать.

Главная экономия — сейчас правильно оптимизировать видео, не хранить мусор в storage и не плодить три независимые базы для сайта и ботов.
