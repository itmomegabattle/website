# Аудит производительности и безопасности Megabattle

Дата замера: 30 июля 2026  
Контур: production-сборка frontend, локальные production preview и тесты backend/bot  
Целевая нагрузка: 1000 зарегистрированных пользователей, до 500 одновременных посетителей

## Краткий итог

Сайт уже не является «тяжёлым приложением» по объёму JavaScript: основной JS-бандл после сборки занимает 370,78 КБ без сжатия и 119,62 КБ gzip. Основная нагрузка создаётся не логикой React, а медиа:

- фоновым видео главной страницы;
- фотографиями на страницах «Люди» и «История»;
- декодированием изображений и видео браузером;
- анимацией фона и GPU-композитингом;
- одноразовым видео-прелоадером.

Именно декодирование видео, CSS-эффекты и одновременное появление множества изображений могут запускать вентиляторы ноутбука. Размер переданных файлов и `usedJSHeapSize` не равны общему потреблению памяти вкладкой: декодированные кадры видео, изображения, GPU-текстуры и compositor layers находятся вне JS heap.

После текущей оптимизации:

- убрана загрузка всех страниц и всех изображений «на будущее»;
- прелоадер показывается только при первом открытии, а не при каждом переходе;
- переходы между страницами больше не применяют дорогой blur ко всей странице;
- изображения команды загружаются порциями;
- 20 тяжёлых архивных фотографий истории повторно сжаты;
- загрузки из админки на клиенте уменьшаются и перекодируются;
- фон упрощён на мобильных и слабых устройствах;
- тяжёлая Three.js-модель находится в отдельном ленивом чанке и не загружается при обычном просмотре.

## Кэш, cookies и прелоадер

Прелоадер не записывает тяжёлые данные в cookie. В cookies/локальном хранилище находится только небольшой признак того, что пользователь уже видел вступление, и данные сессии авторизации. Видео, картинки, JS и CSS сохраняются браузером в HTTP cache/CDN cache.

Текущая модель:

1. при первом визите показывается видео-прелоадер;
2. параллельно браузер начинает загружать код и первый экран;
3. при внутренних переходах прелоадер больше не показывается;
4. после бездействия может быть подогрет код только одного вероятного следующего маршрута;
5. изображения остальных страниц заранее не скачиваются.

Это существенно дешевле прежней схемы с предварительной загрузкой всех страниц.

## Загрузки через админку

Клиент перед загрузкой пытается перекодировать изображения:

| Тип | Максимальная сторона | Целевой предел |
|---|---:|---:|
| Аватар | 640 px | 180 КБ |
| Превью | 800 px | 260 КБ |
| Контентное изображение | 1280 px | 520 КБ |

SVG/GIF ограничены 1 МБ. Однако клиентская проверка не является границей безопасности: изменённый клиент может отправить другой MIME, слишком большой файл или вредоносное содержимое через подписанный URL. Поэтому в production нужен серверный этап после загрузки:

1. прочитать реальные байты объекта;
2. определить формат по содержимому, а не по заголовку;
3. декодировать изображение;
4. ограничить размеры и число пикселей;
5. заново перекодировать в WebP/AVIF;
6. удалить исходный или отклонённый объект.

## Аудит безопасности

### Исправлено в коде

- добавлены базовые HTTP security headers;
- внешние ссылки с `target="_blank"` получают `noopener noreferrer`;
- production backend отклоняет publishable key вместо service-role key;
- production backend проверяет роль внутри JWT service-role key;
- bootstrap-администратор привязывается к неизменяемому Telegram ID, а не к username;
- для хранилища паролей добавлено ограничение попыток PIN: 5 за 15 минут;
- создана SQL-миграция, запрещающая прямой вызов привилегированных RPC через `anon` и `authenticated`;
- backend и bot проходят `npm audit` без известных уязвимостей;
- исправлены уязвимые транзитивные зависимости backend.

Критичная миграция:

`work/imb_backend/supabase/migrations/202607300001_lock_down_backend_rpcs.sql`

Её необходимо применить в Supabase. Пока она не применена в production-базе, некоторые `security definer` RPC могут оставаться вызываемыми напрямую через Supabase API.

### Остаточные риски

| Приоритет | Риск | Что сделать |
|---|---|---|
| Критический | Telegram bot token и Supabase service-role key ранее попадали в локальные env/рабочий контекст | Перевыпустить bot token в BotFather и service-role/secret в Supabase, затем обновить Vercel и bot |
| Критический | Новая RPC-lockdown миграция ещё должна быть применена к production БД | Выполнить SQL-миграцию в Supabase и проверить health endpoint |
| Высокий | Ограничители запросов backend хранят состояние в памяти отдельного serverless instance | Перенести rate limit и одноразовые состояния в Redis/Upstash или Postgres |
| Высокий | Vault использует четырёхзначный PIN, сырой PIN временно хранится в `sessionStorage` | Выдавать короткоживущий серверный unlock-grant; хранить хэш PIN через Argon2id/scrypt; для админов добавить WebAuthn/MFA |
| Высокий | Сервер доверяет клиентской обработке загружаемых изображений | Добавить post-upload worker/webhook с проверкой и повторным кодированием |
| Средний | Строгий Content-Security-Policy пока не включён | Убрать оставшиеся inline-style зависимости и добавить CSP с точным allowlist |
| Средний | Публичные граф и NFC-метаданные позволяют массовый сбор социальных связей | Минимизировать публичные поля, ограничить пагинацию/частоту, рассмотреть opt-out |
| Средний | 30-дневная sliding session увеличивает окно риска при краже cookie | Добавить список активных сессий, принудительный logout-all и ротацию refresh/session token |
| Средний | Frontend audit показывает 2 high для React Router RSC CSRF | Текущий Vite SPA не использует уязвимый RSC/framework path; перейти на исправленную версию после её выпуска или отдельно протестировать миграцию на React Router 8.3+ |

Секреты не входят в git и не обнаружены в production `dist`, но одного этого недостаточно: уже раскрытый секрет нужно именно перевыпустить, а не только удалить.

## Требования к инфраструктуре

### Frontend

Frontend является статическим SPA и должен обслуживаться через CDN. Для 1000 пользователей отдельный мощный frontend-сервер не нужен.

Для всплеска в 500 одновременных мобильных первых открытий при текущем hero:

- только стартовая передача может составить около 2 ГБ;
- видео должно отдаваться CDN с Range Requests;
- статика должна иметь versioned immutable cache;
- исходящие запросы не должны проходить через Node backend.

Практический вариант: Vercel/Cloudflare Pages/статический Nginx + CDN.

### Backend

Backend: Node.js 22 + Fastify + TypeScript, stateless API поверх Supabase/PostgreSQL.

Рекомендуемый старт для 500 одновременных посетителей:

- минимум: 2 vCPU, 4 ГБ RAM;
- спокойный production-запас: 4 vCPU, 8 ГБ RAM;
- 2 процесса/реплики за reverse proxy;
- Redis 256–512 МБ для rate limits, nonce, временных login/NFC состояний и очередей;
- фоновые уведомления и обработку медиа запускать отдельным worker, а не внутри web-процесса.

Если backend остаётся serverless, CPU/RAM экземпляра менее важны, но обязательны внешний Redis и контроль лимитов времени выполнения.

### PostgreSQL / Supabase

Для 1000 профилей сами структурированные данные очень малы. Основной рост создают audit logs, уведомления, связи графа, транзакции валюты и регистрации.

Стартовая конфигурация:

- PostgreSQL: 2 vCPU, 2–4 ГБ RAM;
- диск: 20 ГБ с автоматическим расширением;
- ежедневные backup + point-in-time recovery перед production;
- connection pooler;
- индексы по Telegram identity, profile ID, friendship endpoints, event/team code, notification status и timestamp;
- изображения и видео хранить только в object storage, не в строках БД.

Object storage:

- начать с 20–50 ГБ;
- оригиналы пользовательских изображений удалять после успешного перекодирования;
- временные фото с TTL удалять lifecycle policy, а не только cron-задачей приложения.
