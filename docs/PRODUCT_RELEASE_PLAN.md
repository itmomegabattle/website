# ITMO Megabattle Website — состояние проекта и план до сильного релиза

Дата актуализации: 6 июля 2026  
Цель документа: зафиксировать, что уже есть, что нужно добить, где есть риски, и в каком порядке довести сайт до почти продакшен-качества.

## 1. Главный вывод

Проект уже вырос из “просто сайта” в экосистему:

- сайт;
- личные профили участников;
- NFC-визитки;
- рейтинг и граф знакомств;
- админка;
- загрузка и модерация контента;
- будущий ITMO.ID;
- Telegram Mini App;
- два Telegram-бота;
- интеграция с ITMO Events;
- рассылки;
- временные фото в стиле Locket с удалением через час.

Поэтому дальше проект нельзя держать только на frontend + Supabase policies. Supabase стоит оставить как базу, auth/storage и быстрый managed Postgres, но нужен отдельный backend API как центральный слой логики.

Рекомендуемая целевая архитектура:

```text
Frontend / сайт / Telegram Mini App
        ↓
Backend API
        ↓
Supabase Postgres + Supabase Storage
        ↓
ITMO.ID / ITMO Events / Telegram Bots / рассылки / фоновые задачи
```

Свой backend не означает уход от Supabase. Наоборот: Supabase остаётся базой и хранилищем, а backend становится “мозгом”, который безопасно управляет интеграциями, правами, рейтингами, графом, ботами и временными файлами.

Главная боль сейчас: мобильный hero-video грузит слишком долго или не грузит нормально.

Вероятные причины:

- слишком тяжёлый файл;
- слишком высокий bitrate;
- неподходящий codec/profile для части телефонов;
- нет нескольких quality-версий;
- видео грузится слишком рано;
- нет жёсткой стратегии `poster first, video later`;
- возможно, mobile-сеть/браузер режет autoplay heavy video.

Что нужно сделать:

1. Пересобрать mobile hero-video отдельно:
   - 720×1280 или ниже, если визуально ок;
   - H.264 baseline/main для совместимости;
   - отдельный `.webm` как дополнительный источник;
   - bitrate примерно 1.2–2.5 Mbps, тестировать глазами;
   - длительность только нужная, без лишних секунд;
   - audio удалить;
   - faststart/moov atom в начало.

2. Сделать несколько вариантов:
   - `hero-mobile-540p.mp4`
   - `hero-mobile-720p.mp4`
   - `hero-desktop-1080p.mp4`
   - `hero-desktop-720p.mp4`

3. На mobile:
   - сначала показывать poster;
   - видео подгружать после preloader или после первого idle;
   - если видео не стартовало за 2–3 секунды — оставить poster, не ломать UX.

4. Не грузить desktop-video на mobile вообще.

5. Не грузить mobile-video на desktop вообще.

6. Добавить проверку:
   - iPhone Safari;
   - Android Chrome;
   - Telegram in-app browser;
   - плохая сеть.

## 3. Почему нужен backend

По текущим требованиям backend нужен не “для красоты”, а чтобы проект не стал небезопасным и неуправляемым.

Требования, которые требуют server-side логики:

- ITMO.ID;
- хранение `client_secret`;
- Telegram-боты;
- Telegram Mini App;
- ITMO Events API;
- рассылки;
- загрузка участников из таблиц;
- рейтинг;
- граф знакомств;
- NFC;
- временные фото с удалением через час;
- защита от накруток;
- логи;
- админские действия;
- пиковая нагрузка до 3000 пользователей.

Frontend не должен:

- хранить секреты;
- напрямую решать, кто админ;
- пересчитывать рейтинги как источник истины;
- валидировать дружбы как источник истины;
- выполнять фоновые задачи;
- удалять временные фото по расписанию;
- общаться с ITMO Events с приватными ключами;
- управлять ботами.

## 4. Оставляем Supabase или уходим?

Уходить от Supabase сейчас не нужно.

Supabase стоит оставить как:

- Postgres;
- Storage;
- быстрый auth на переходный период;
- realtime, если понадобится;
- managed-инфраструктура без администрирования базы.

Но нужно добавить backend API поверх Supabase.

Правильный переход:

```text
Сейчас:
Frontend → Supabase

Переходный этап:
Frontend → Supabase для простого чтения
Frontend → Backend для опасных/сложных действий
Backend → Supabase service role

Цель:
Frontend / Mini App / Bots → Backend API → Supabase
```

Что можно оставить напрямую через Supabase:

- публичное чтение опубликованного контента;
- простые user-profile reads;
- storage public URLs.

Что нужно увести в backend:

- ITMO.ID auth callback;
- выдача/проверка сессий;
- админские действия;
- создание/модерация/удаление контента;
- регистрация на мероприятия;
- рейтинги;
- дружбы;
- NFC;
- боты;
- временные фото;
- рассылки;
- интеграции.

## 5. Рекомендуемый backend stack

### 5.1. Язык и фреймворк

Рекомендация: `Fastify + TypeScript`.

Почему:

- быстрее поднять, чем NestJS;
- меньше церемоний;
- хорошая производительность;
- удобные плагины;
- легко сделать REST API;
- достаточно строго с TypeScript;
- хорошо подходит маленькой команде.

Альтернатива: `NestJS`.

Когда выбрать NestJS:

- если заранее понятно, что будет много модулей;
- если нужны DI, guards, decorators, CQRS;
- если проект будет развиваться большой командой.

На текущий момент Fastify практичнее.

### 5.2. Хостинг backend

Варианты:

1. Railway / Render / Fly.io
   - быстро стартовать;
   - меньше настройки;
   - удобно для MVP;
   - может быть дороже/менее предсказуемо на длинной дистанции.

2. VPS: Timeweb Cloud / Selectel / Reg.ru Cloud / Hetzner
   - больше контроля;
   - дешевле на дистанции;
   - можно держать бота, API, cron;
   - нужно администрирование.

3. Vercel serverless
   - можно для простых API;
   - плохо для ботов, фоновых задач и долгоживущих процессов;
   - не лучший выбор для центрального backend.

Рекомендация:

- сайт оставить на Vercel;
- backend поднять отдельно;
- Supabase оставить отдельно;
- домен настроить так:
  - `megabattle.itmo...` или основной домен — сайт;
  - `api.domain.ru` — backend;
  - `admin.domain.ru` опционально позже;
  - `t.me/...` — боты.

## 8. Безопасность

### 8.1. Что сейчас рискованно

- Часть действий всё ещё может идти напрямую с фронта в Supabase.
- Админская логика частично на клиенте.
- Рейтинги/дружбы/NFC пока не полностью централизованы на сервере.
- Пароли проекта — чувствительная зона, нужен максимально аккуратный подход.
- Storage uploads нужно ограничивать по размеру/типу.
- ITMO.ID нельзя делать полностью на фронте, если есть `client_secret`.

### 8.2. Что нужно сделать

- Все секреты только на backend.
- Supabase service role только на backend.
- На frontend только anon key.
- Для опасных действий — backend endpoints.
- Rate limit:
  - login;
  - NFC claim;
  - add friendship;
  - upload;
  - story submit;
  - registrations.
- Audit logs для админки.
- Soft delete для людей/мероприятий/партнёров/профилей.
- Проверка file MIME + size.
- Virus scan опционально позже.
- CSP/security headers.
- Backups Supabase.

## 9. Performance и оптимизация сайта

### 9.1. Главные проблемы

1. Mobile hero-video не грузится нормально.
2. Большие JS chunks из-за Three.js/preloader/графа.
3. Возможные CLS из-за background SVG/видео/изображений без размеров.
4. Не все изображения имеют `width`/`height`.
5. Часть CSS не используется на первом экране.
6. Яндекс/карты/метрика могут добавлять лишний JS.
7. Граф знакомств может положить страницу при большом числе вершин.

### 9.2. Видео

Нужно сделать отдельный pipeline оптимизации видео.

Для hero:

- desktop:
  - 1920×1080 или 1600×900;
  - H.264;
  - WebM VP9/AV1 опционально;
  - target size желательно до 8–15 MB, если возможно.

- mobile:
  - 720×1280 или 540×960;
  - H.264;
  - target size желательно до 3–6 MB;
  - poster обязателен;
  - audio отсутствует.

Поведение:

- poster показывается сразу;
- видео не должно блокировать первый рендер;
- если mobile video не стартует быстро — остаётся poster;
- `preload="metadata"` или lazy-load после preloader;
- media queries/source type, чтобы не качать лишнее.

### 9.3. Preloader

Preloader должен:

- быть единым на всех страницах;
- грузиться быстро;
- иметь poster;
- не грузить 3D runtime;
- не показываться бесконечно;
- не вызывать CLS;
- иметь fixed контейнер;
- иметь минимальную длительность;
- исчезать резким, но аккуратным переходом после завершения видео.

### 9.4. Code splitting

Нужно вынести тяжелые вещи в lazy chunks:

- `three`;
- `GLTFLoader`;
- `MovingHeadScene`;
- `FriendshipGraph`;
- admin panels;
- возможно QR/social modal.

Цель:

- главный bundle меньше;
- главная страница не тянет код графа/админки;
- страницы грузят только нужный JS.

### 9.5. Images

Нужно:

- всем `img` задать width/height или aspect-ratio контейнер;
- использовать WebP/AVIF;
- сделать small/big версии;
- lazy loading для всего ниже первого экрана;
- `fetchpriority="high"` только для реально важного изображения;
- нормальные alt.

### 9.6. Graph optimization

Для графа:

- не рендерить 1000+ DOM-элементов;
- использовать Canvas/WebGL;
- показывать кластеры;
- ограничивать первый viewport;
- при клике раскрывать соседей;
- сервер отдаёт подграф, а не всё всегда;
- на mobile показывать simplified view.

## 14. Что нужно решить по домену

Домен критичен, потому что NFC-метки будут физически записаны на ссылки.

Нужно:

- купить домен на много лет;
- включить автопродление;
- держать доступы не у одного человека;
- записать registrar/account в админском хранилище паролей;
- настроить:
  - `www`;
  - root domain;
  - `api`;
  - возможно `nfc`;
  - возможно `admin`;
- не использовать временный vercel URL в NFC для продакшена.

Для NFC лучше иметь короткий стабильный путь:

```text
https://domain.ru/n/<tagCode>
```

или:

```text
https://n.domain.ru/<tagCode>
```

## 19. Самые большие риски

1. Mobile video performance.
2. Разрастание логики на frontend без backend.
3. ITMO.ID доступы могут задержаться.
4. NFC-ссылки нельзя потом легко менять, если записать неправильный домен.
5. Граф может стать тяжёлым при реальных данных.
6. Telegram Mini App и боты быстро потребуют общей авторизации.
7. Storage может разрастись без cleanup.
8. Админские действия без backend сложнее защищать.
9. Пиковые моменты на мероприятиях могут вскрыть слабые места.

## 20. Итоговое решение по архитектуре

Финальное направление:

- Supabase оставляем.
- Vercel оставляем для frontend.
- Добавляем отдельный backend.
- Backend становится обязательным API для сложных и опасных действий.
- ITMO.ID делаем через backend.
- Telegram bots и Mini App делаем через backend.
- Видео оптимизируем как отдельный critical task.
- Редактируемые разделы постепенно переводим полностью на БД.
- JSON оставляем как fallback/seed/static.

Это самый безопасный путь к сильному продукту без полного переписывания того, что уже сделано.
