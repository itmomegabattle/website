Дата: 25 июля 2026

1. ЧТО И КАК ИЗМЕРЯЛОСЬ

Проверена локальная production-сборка Vite на восьми публичных маршрутах:
/, /people, /faculties, /history, /partners, /events, /ratings, /auth.

Для каждой страницы Chrome запускался заново с пустым кешем. Это важно:
память предыдущей страницы не попадала в следующую. После загрузки страница
оставалась открытой 4,2 секунды, чтобы успели завершиться запросы и основные
анимации.

После оптимизации выполнены два отдельных прогона:
- FIRST — самое первое открытие сайта, когда прелоадер ещё показывается;
- RETURNING — любое следующее открытие или переход после первого просмотра:
  браузер уже хранит версию просмотренного прелоадера и не запрашивает его видео.

Профили:
- desktop: 1440 × 900;
- mobile: 390 × 844.

В таблицах:
- JS heap — память JavaScript после стабилизации страницы. Это не вся RAM
  процесса Chrome, а сопоставимый показатель объёма живых JS-объектов;
- трафик — фактически переданные байты при первом холодном открытии;
- decoded — размер загруженных ресурсов после декодирования;
- DOM — количество элементов страницы;
- запросы — все сетевые запросы страницы;
- высота — полная высота документа в CSS-пикселях.

На реальном Vercel значения могут немного отличаться из-за CDN, кеша, HTTP/2/3
и сетевого диапазонного чтения видео. Сравнение страниц между собой корректно.

4. ЧТО СЕЙЧАС САМОЕ ТЯЖЁЛОЕ

1) Главная на мобильном остаётся самым тяжёлым первым экраном: 6,15 МБ при
   первом входе и 5,79 МБ после него. Главная причина — мобильный hero-ролик
   размером 4,21 МБ. Прелоадер теперь добавляет только 0,36 МБ один раз.

2) История — самая длинная страница:
   386 DOM-элементов, 13 453 px на desktop и 12 129 px на mobile.
   Холодный трафик — около 3 МБ, из них примерно 1,6 МБ изображения и 1,1 МБ
   общий видео-прелоадер. JS-память при этом небольшая — 2,4 МБ.

3) Люди — наибольший JS heap на mobile (5,1 МБ), 601 DOM-элемент и до
   4,27 МБ холодного трафика на desktop. Причина — 23 карточки команды,
   фотографии, истории и интерактивный граф знакомств на одной странице.

4) Факультеты — около 2,4 МБ трафика и высокая мобильная страница (6042 px).
   Во время первого прогона декоративный фон расширял документ на 14–22 px.
   Переполнение исправлено глобальным ограничением корневого элемента; повторная
   проверка показывает scrollWidth == clientWidth.

5) Обычные страницы больше не платят за прелоадер при навигации. Например,
   /auth снизился с прежних 1,45 МБ до 0,74 МБ на самом первом входе и до
   0,32 МБ на всех последующих открытиях.

Во время визуальной проверки обнаружено, что успешный, но пустой ответ backend
отключал JSON-fallback. Из-за этого могли исчезать команда, истории, партнёры и
мероприятия без явной ошибки в консоли. Переходный слой исправлен: непустая БД
остаётся источником истины, а при пустой БД показывается локальный контент.
Цифры в таблицах получены уже после этого исправления, с полным контентом.

- HomePage: 42,70 КБ / 8,79 КБ;
- PeoplePage: 29,74 КБ / 6,43 КБ;

Vite предупреждает только о чанке Three.js больше 500 КБ. Three.js, GLTFLoader
и GLB относятся к исходнику генерации прелоадера. В обычном пользовательском
режиме они больше не импортируются и не запрашиваются: отдельный динамический
чанк PreloaderCapture (7,18 КБ / 3,19 КБ gzip) открывает их только по служебному
URL ?capturePreloader=1. Этот режим сохранён для будущей пересборки видео.

- public/models/moving-head-beam-high-poly.glb — 1,90 МБ;
- public/videos/preloader-desktop.mp4 — 1,20 МБ;
- public/videos/preloader-mobile.mp4 — 1,13 МБ;
- public/images/about-image.png — 0,79 МБ;
- отдельные большие портреты команды — до 0,51 МБ каждый.

Размер hero-video.mp4 не равен трафику первых 4,2 секунды: браузер читает MP4
диапазонами. Но при полном просмотре desktop-ролика браузер в обычном случае
докачает почти весь файл: 16 476 504 байта, то есть 16,48 МБ в десятичной
системе или 15,71 МиБ. Это не значит, что каждый повтор петли снова скачивает
16,48 МБ: пока ресурс есть в HTTP/browser cache, повторное воспроизведение
использует кеш. При первом полном просмотре к этим 16,48 МБ добавляются остальные
ресурсы страницы.

8. ПРИОРИТЕТЫ БУДУЩЕЙ ОПТИМИЗАЦИИ

P0. Главная
- Для мобильного hero подготовить ещё более лёгкий AV1/WebM вариант и MP4 fallback.
- Проверить moov atom (fast start), GOP и битрейт; качество сохранять через
  perceptual encoding, а не простое уменьшение разрешения.
- Для desktop подготовить WebM/AV1 вариант; сейчас полный просмотр — 16,48 МБ.

ВЫПОЛНЕНО: прелоадер
- показывается только один раз для текущей версии в данном браузере;
- не появляется на переходах React Router и после перезагрузки;
- одновременно с ним приложение монтируется и загружает текущую страницу;
- использует WebM первым и MP4 как совместимый fallback;
- 3D/Three.js/GLB исключены из пользовательских запросов;
- исходник 3D и скрипт render:preloader сохранены для пересборки.

P1. Изображения
- Сделать responsive-наборы 320/640/960/1440 и использовать srcset/sizes.
- PNG без прозрачности перевести в AVIF/WebP.
- Для карточек людей не отдавать big-версию до открытия подробного профиля.
- Всем изображениям оставить явные width/height или aspect-ratio.

P1. Код и CSS
- Загружать Supabase/auth/admin-код только на маршрутах, где он нужен.
- Разделить page-info.css по доменам (events, faculties, auth/profile, ratings).
- Убрать накопившиеся override-слои в page-history.css после фиксации дизайна.
- Для графа знакомств оставить ленивый mount по IntersectionObserver и не
  создавать renderer, пока пользователь не дошёл до блока.

P2. Данные и внешние виджеты
- Карты, iframe и социальные embed загружать после взаимодействия или появления
  рядом с viewport.
- Историю, события и партнёров отдавать через API с версией/ETag и долгим кешем.
- Сервер не уменьшит вес CSS/JS/видео сам по себе: он полезен для пагинации,
  агрегации, авторизации и кеширования данных, но медиа всё равно нужно сжимать
  и раздавать через CDN/object storage.

P2. Кеш и наблюдаемость
- Для хешированных /assets задать immutable-cache на год.
- Для изображений и видео — CDN cache с версионированными именами.
- Добавить Web Vitals/RUM: LCP, INP, CLS, TTFB и тип соединения пользователя.
- Повторять этот аудит после крупных изменений; скрипт лежит в
  scripts/audit-pages.mjs.


9. ИТОГ

По JS-памяти сайт сейчас не тяжёлый: публичные страницы держатся примерно в
диапазоне 2,3–4,6 МБ heap. Основная проблема — не React и не количество
компонентов, а hero-видео и изображения.

Самая дорогая страница по мобильному холодному трафику — главная: 6,15 МБ при
первом входе и 5,79 МБ после него. Самая дорогая по desktop-контенту — люди:
3,69 МБ в первый раз и 3,26 МБ без прелоадера. Обычные лёгкие страницы после
первого просмотра передают 0,32–0,62 МБ.

Текущий аудит прошёл без runtime/console-ошибок, без HTTP 4xx/5xx и без
горизонтального переполнения во всех 32 проверках: 16 первых и 16 повторных
открытий.

Маршруты /u/:profileId и /nfc/:tagCode не включены в числовую таблицу, потому
что для честной проверки им нужны валидные профиль и NFC-метка из production
данных. Их базовые UI-компоненты покрываются маршрутами /ratings и /auth; перед
релизом нужен отдельный сценарий с тестовыми сущностями.
